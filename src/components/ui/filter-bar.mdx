# Filter Bar

The single filter toolbar for a list page. It is configured by an array of
**facets**: the page describes what it filters on, and the bar decides its own
controls.

## Overview

Every list page needs the same thing — narrow a table by a handful of enumerated
fields, a date range and a free-text match, and keep the result shareable. Left
to themselves, pages each grow a chip row plus a rank of dropdowns, and the
copies drift. Filter Bar replaces that with one component whose entire appearance
comes from `facets`, so a new list page is a config, not a layout.

## Usage

- **Do** derive `facets` from the page's existing filter-options endpoint.
- **Do** keep `values` in URL-synced list state so a link reproduces the view.
- **Do** order facets by reach: the most-used first, date and free text last.
- **Don't** add a page-local Apply button — filtering is live; `Done` only closes.
- **Don't** fabricate `count`. Omit it and the count column does not render.
- **Do** pass `calendar` + `locale` on a surface whose language is not the
  browser's. A native date field draws the BROWSER's calendar and takes no
  instruction about it, so it is the one control here that cannot otherwise
  follow the app.
- **Do** pass `formatCount` in an app whose language is a user preference. The
  default reads the *runtime's* locale, which follows the machine, not the app —
  a Persian page in an `en-US` browser prints `1,234` beside Persian labels.

## Anatomy

A toolbar row — the **Filters** trigger (`sliders-horizontal`, the active-facet
count badge, an `F` key hint), a **summary sentence**, a **Clear** link, a
**copy-link** button and a `SearchInput` — above a portalled 520px panel split
into a 172px **facet rail** and a **facet pane** (header with a per-facet Clear,
the control, and a footer carrying the live result line, **Clear all** and
**Done**).

The summary sentence replaces the conventional chip row. Chips cost a whole row
of vertical space to say what one sentence says, and they push the table further
down as filters accumulate; removing a single value happens in the panel, where
the rest of that facet is visible anyway.

## Facet types

- `multi` — a scrollable checkbox list with an optional per-option `count`. Add
  `searchable` for a client-side option filter. The list is sized by the
  RESPONSE, not by the design, so it windows itself past ~60 options: only the
  rows near the viewport are in the DOM. Pass the whole option set — there is no
  count at which you should truncate it yourself.
- `date` — four presets (Last 7 / 30 / 90 days, All time) plus From / To fields,
  optionally bounded by `min` / `max`. Pass those bounds in whatever ISO shape
  the endpoint sends them; they are narrowed to a day before they reach the
  field, because a native date input drops a `min` / `max` it cannot read as
  `YYYY-MM-DD` instead of reporting it. Under a non-Gregorian `calendar` the
  same two fields are built from `Date Picker` instead — see **Calendars**.
- `text` — a single "contains" field.

## Behavior

- **Live apply.** Every change fires `onChange` at once; the footer's result line
  updates under the user's hand, which is what makes the panel worth opening.
- **Selected-first ordering.** Selected options are hoisted to the top of a
  `multi` list, tinted, and separated by a hairline. The sort is captured **on
  open and on facet switch — never on click**, because re-sorting live would
  slide a row out from under the pointer as it is being checked.
- **The active facet is resolved, not assumed.** The facet set can change under
  an open panel (an org switch, a wizard step re-filtering its options), so a
  held id that no longer exists falls back to the first facet instead of
  rendering a blank pane.
- **Scale is the component's problem, not the page's.** A facet's option count is
  whatever the filter-options endpoint sends — thousands, for registrars or CVEs
  — and both the rail and the option list absorb it: the rail scrolls inside the
  panel instead of stretching it past the viewport, and a `multi` list past ~60
  options renders only the rows near its viewport against a full-height scroll
  range. Ranking and membership are `Map`/`Set` lookups, so a wide facet costs no
  more per keystroke than a narrow one.
- **The pane sets the panel's height; the rail follows it.** The pane grows with
  its own contents — a searchable facet's option-search field alone adds ~104px —
  so the rail is stretched to the row rather than capped, and always meets the
  footer. It never leaves a bare strip beneath the last facet, and never pushes
  the panel taller than the pane needs.
- **Keyboard.** `F` opens the panel from anywhere on the page, `/` focuses
  search, `Escape` closes. Both hints are shown, not hidden. In a windowed option
  list, arrow keys (plus `Home` / `End`) move between rows — Tab alone cannot
  cross a boundary where the next row is not yet rendered.
- **A backwards date range is prevented first and reported second.** The two
  fields of a `date` facet bound each other — the chosen end day caps the start
  calendar, the chosen start day floors the end one — so the ordinary path
  through the control cannot produce a range that matches nothing. The calendar
  is not the only way in, though: a day can be typed, and a whole range arrives
  from a deep link having never passed through this component. When one lands
  backwards anyway both fields go `aria-invalid` and the pair is explained
  beneath them, the rail entry reads `invalid`, and the trigger's count turns
  destructive so the state survives the panel being closed. The out-of-range
  value is still shown — blanking what the user typed would leave nothing to
  correct. **Not submitting it is the page's job**, not the bar's; the bar
  filters live, so a list that keeps sending a backwards range gets an empty
  table with no explanation.
- **Options loading / error** are contained to the pane: placeholder rows or a
  retry. A facet-options failure must never block the list itself, and filters
  restored from a deep link still apply without options having loaded.

## Accessibility

- The trigger is a real popover trigger with `aria-expanded`; the panel is
  portalled and dismisses on `Escape` / outside press with focus returned.
- Option rows carry `role="checkbox"` + `aria-checked` and are labelled by their
  option text; the list is a labelled `group`. When the list is windowed the rows
  stay direct children of that group — the scroll spacer between them is
  `role="presentation"` — and arrow keys address rows by index, so every option
  is reachable even though most are not materialised.
- Set facets are marked by a count *and* a dot beside the label — never colour
  alone. An unusable one is marked the same way: the rail's summary word becomes
  `invalid`, so the destructive tint is never carrying the meaning by itself.

## Design tokens

Surfaces `--card` / `--surface` / `--surface-2`; `--border`; `--foreground` /
`--muted-foreground`; `--primary` / `--accent-strong` / `--accent-soft`;
`--ring`. Counts use `--font-mono` with `tabular-nums`. Radius: panel 12,
controls 10, rows and chips 7–8. Elevation `--elevation-3`. No hard-coded colour.

## API

| Prop | Type | Default | Description |
| --- | --- | --- | --- |
| `facets` | `FilterBarFacet[]` | — | Facets, in rail order. Required. |
| `values` | `Record<string, string[] \| {from,to} \| string>` | — | Value per facet id. |
| `onChange` | `(facetId, value) => void` | — | Fires on every change. |
| `onClear` | `() => void` | — | Clears every facet. |
| `search` / `onSearch` | `string` / `(v) => void` | — | Toolbar search. |
| `searchPlaceholder` | `string` | `"Search"` | Search placeholder. |
| `resultLine` | `string` | — | Live result count in the panel footer. |
| `onCopyLink` | `() => void` | — | Shows the copy-link button; the bar copies the URL, the page confirms. |
| `loading` / `error` / `onRetry` | `boolean` / `boolean` / `() => void` | `false` | Facet-options async states. |
| `labels` | `Partial<FilterBarLabels>` | English | Every string the bar renders on its own account. |
| `calendar` | `"gregory" \| "persian"` | `"gregory"` | Calendar a `date` facet is picked in. |
| `locale` | `string` | runtime | BCP-47 locale for that calendar's names and digits. |
| `formatCount` | `(value: number) => string` | `v => v.toLocaleString()` | Every NUMBER the bar renders on its own account: option counts, the trigger badge, the summary count. |

The API is closed: `className` and `style` are not accepted.

## Calendars

A `date` facet is two native date fields, which is the right control wherever it
can express the calendar: it can be typed into, it carries the platform's own
picker, and it reaches a day a year away without a popover. What it cannot do is
be TOLD which calendar to draw — it follows the browser — so on a Persian page it
is Gregorian for most people, Jalali for a few, and unaskable in either case.

`calendar="persian"` therefore swaps that pair for AEGIS `Date Picker`s drawing a
true Jalali month. Everything else about the facet is unchanged, including the
bounding, the invalid marking, the message, and — the part that matters
downstream — the VALUE: `{from, to}` stays `YYYY-MM-DD` Gregorian in every
calendar, so a page's request, its query string and its shareable link are
identical whichever calendar the user picked in.
